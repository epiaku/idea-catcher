# Gemini video fallback: promising but not yet safe

Gemini's native video-understanding API can genuinely process a bare YouTube URL — no download, no captions required — by decoding audio and visual frames directly, and it works today on a free API key subject only to an **8-hour-per-day** duration cap ([Video understanding](https://ai.google.dev/gemini-api/docs/video-understanding)). But it should **not** be adopted as idea-catcher's fallback yet: real-world reports from `googleapis/python-genai` GitHub issues, the official Google AI Developer Forum, and at least one comparable production pipeline (`dzivkovi/video-intel`) describe a multi-faceted reliability problem — intermittent 400 errors that succeed on blind retry, silent first-call transcript truncation with no error signal, drifting timestamps, and unbounded processing time on long videos — none of which are acknowledged or resolved by Google as of this research (Sept 28, 2026). Given that idea-catcher's existing two-tier fallback (`youtube_transcript_api` → `yt-dlp` subtitles) already suffers from YouTube-side blocking, adding Gemini as a third tier is technically straightforward and cheap (roughly **$0.27–$0.81 per hour of video** analyzed), but it substitutes one unreliable, semi-documented dependency for another rather than solving the underlying scraping-fragility problem. The stronger near-term fix is hardening the existing two tiers — via `yt-dlp`'s independent request path and, if blocking persists, a rotating residential proxy — with Gemini positioned as an **optional, heavily-guarded fourth tier**, not the primary answer to transcript-fetch failures.

## Gemini decodes video directly and doesn't need YouTube's captions

The mechanism itself is sound: Gemini's video understanding samples frames at 1 FPS and tokenizes raw audio, rather than ingesting YouTube's caption track — a person passing `types.Part(file_data=types.FileData(file_uri=<youtube_url>))` to `client.models.generate_content()` gets audio- and visual-stream analysis, not a caption lookup ([Video understanding](https://ai.google.dev/gemini-api/docs/video-understanding)). This is architecturally distinct from Google's separate consumer-facing "Ask about this video" feature inside the YouTube app, which one third-party source describes as caption-dependent and blind to on-screen content the narration doesn't mention ([datastudios.org](https://www.datastudios.org/post/can-google-gemini-summarize-youtube-videos-video-understanding-and-summary-reliability)) — the two are easy to conflate but should not be, since idea-catcher would use the API path, not the app feature. Only public videos are supported; private and unlisted YouTube links are explicitly rejected with no authenticated-access exception ([Video understanding](https://ai.google.dev/gemini-api/docs/video-understanding)), which matters if idea-catcher ever needs to process unlisted drafts. Video length scales with context window and resolution setting — a 1M-context model handles up to roughly 3 hours at low resolution or 1 hour at high resolution, per the most detailed verbatim quote found, though a separate doc pass gave slightly different figures that could not be fully reconciled in this research pass. There's no dedicated "give me a transcript" API flag; a transcript-like, quotable output has to be prompt-engineered — asking the model to emit `MM:SS — text` lines — and then parsed by the calling code, since Gemini returns free text, not a structured caption object.

## Free tier works, but pricing math and EEA/UK terms complicate the picture

Access itself is not gated behind billing: a free API key can call the YouTube-URL feature today, capped at 8 cumulative hours of video per day, versus no length-based cap on paid tiers ([Video understanding](https://ai.google.dev/gemini-api/docs/video-understanding)). That said, **in the EEA, Switzerland, and the UK, Google's Additional Terms restrict API clients to Paid Services only** ([Gemini API Additional Terms of Service](https://ai.google.dev/gemini-api/terms)), which functionally removes free-tier access for any client made available to users in those regions — worth flagging explicitly if idea-catcher or its users are EU-based. Pricing itself is billed as ordinary input tokens, not a dedicated per-second video rate: Google's docs put video at roughly **100 tokens/second at low (default) resolution or ~300 tokens/second at high resolution** ([Video understanding](https://ai.google.dev/gemini-api/docs/video-understanding)). Combined with Gemini 3.8 Flash's reported introductory rate of $0.75/M input tokens, that works out to roughly **$0.27/hour of video at low resolution, or ~$0.81/hour at high resolution** — these are derived calculations, not numbers Google states directly, and the model's exact current per-token price could not be independently confirmed on the live pricing page in this research pass (third-party aggregator only). One documentation inconsistency is worth flagging rather than resolving: an older doc line still claims "the YouTube URL feature is in preview and is available at no charge," which appears to contradict the standard token-billing framing found elsewhere and is likely stale. A long video also has a practical rate-limit consequence: a 1-hour video can consume 360,000–1,080,000 input tokens in a single call, which can exceed a lower usage tier's entire per-minute token budget on its own — meaning general TPM limits, not a video-specific quota, are the likely binding constraint for anything but short clips. No source found tested output determinism specifically for video understanding; the closest evidence is a Google forum thread showing **non-deterministic output even with a fixed seed and low temperature** on an unrelated image-analysis task ([forum thread](https://discuss.ai.google.dev/t/the-gemini-api-is-exhibiting-non-deterministic-behavior-for-the-gemini-2-5-pro-model-it-is-producing-different-outputs-for-identical-requests-even-when-a-fixed-seed-is-provided-along-with-a-constant-temperature-this-behavior-has-been-reliably-rep/101331)), so idea-catcher should not assume identical output across repeated runs on the same video.

## Independent bug reports converge on a genuine, unresolved reliability gap

This is the strongest and most consequential finding: **multiple, independent reporters describe the same class of problem, and none of it is officially acknowledged as fixed.** A controlled test posted to the Google AI Developer Forum ran 100 identical requests against a single video via Vertex AI's Gemini 2.5 Flash and got mixed results across two runs — 91–95 successes out of 100, with the remainder split between 400 errors and timeouts — and the same pattern held across 95 distinct videos, with videos that failed on one attempt typically succeeding on retry; the reporter's core complaint is that Google returns a **non-retryable 400 for what is empirically a transient, retryable server-side failure**, and no official Google reply appears in the thread ([forum thread](https://discuss.ai.google.dev/t/youtube-url-video-input-returns-intermittent-400-invalid-argument-should-be-503-or-retryable-error-code/125883)). Separately, `googleapis/python-genai` Issue #1898 documents a **silent first-call truncation bug**: an uncached, first-time request against a given YouTube video can return a transcript covering as little as 0.5%–27% of the actual video, with `prompt_token_count` identical between the truncated and full runs — meaning there is **no error signal at all**, just quietly wrong output, though a second (cached) call on the same video tends to be reliable ([Issue #1898](https://github.com/googleapis/python-genai/issues/1898)). Related issues report drifting timestamps on long videos (Issue #1359), inconsistent behavior between the YouTube-URL path and the File-API-upload path for identical content (Issue #864), and a possible failure mode for videos less than about a month old (unverified beyond a thread title). Most tellingly, a comparable real-world production system — `dzivkovi/video-intel` — evaluated Gemini for long-video understanding and is actively moving **away** from it toward YouTube's free captions, citing "thinking-budget overflow," "backward jumps," output-cap truncation, and unbounded processing time (a 1h37m video stuck for ~55 minutes) ([Issue #227](https://github.com/dzivkovi/video-intel/issues/227)). This is a practitioner facing precisely idea-catcher's trade-off and choosing the opposite direction for anything but caption-poor content.

## yt-dlp is a genuinely separate path; Gemini adds cost without fixing the root cause

`youtube_transcript_api` and `yt-dlp` hit YouTube through architecturally different channels — the former calls YouTube's public `timedtext` endpoint directly after parsing the video page's `ytInitialPlayerResponse`, while `yt-dlp` POSTs to YouTube's internal Innertube API while impersonating a mobile client ([technical explainer](https://nadimtuhin.com/blog/ytranscript-how-it-works); [technical explainer](https://medium.com/@jallenswrx2016/using-yt-dlp-to-download-youtube-transcript-3479fccad9ea)) — meaning a block scoped to one endpoint's fingerprint plausibly does not immediately affect the other, which is exactly the logic idea-catcher's existing two-tier fallback already relies on. But `yt-dlp` has its own, actively-occurring blocking problems: multiple open issues report `HTTP 429` on subtitle downloads, and a regression as recent as 2026-09-26 notes that forcing the Android client now requires a PO token yt-dlp doesn't yet handle gracefully ([issue tracker](https://github.com/yt-dlp/yt-dlp/issues/13831)) — this path requires ongoing maintenance to keep pace with YouTube's countermeasures. The `youtube_transcript_api` maintainer's own README treats blocking as expected for any non-trivial deployment, especially cloud-hosted ones (AWS/GCP/Azure IP ranges are explicitly called out as commonly pre-blocked), and recommends **rotating residential proxies** (Webshare specifically) over waiting the block out or using cookie auth, which risks a permanent account ban ([README](https://github.com/jdepoix/youtube-transcript-api)). Pricing for that option is low at idea-catcher's likely volume — transcript text is kilobytes per video, so even Webshare's smallest ~1GB/$3.50 tier would cover far more than "a few videos a week," though one unresolved GitHub issue (#511) reports blocking persisting even with Webshare configured, so proxy rotation is not a guaranteed fix either. Waiting out a block is weakly supported: anecdotal community reports suggest a 24–48 hour rate-limit reset window, but the library's own docs describe some bans (static proxies "after extended use") as effectively persistent, and explicitly advise against relying on a wait-it-out strategy.

## Recommendation: harden the existing two tiers first, gate Gemini behind strict checks

The evidence favors a layered response rather than a single fallback swap. First, treat `yt-dlp`'s subtitle path as the immediate, cheap fallback it already should be, keeping it updated frequently given YouTube's shifting client-fingerprint requirements. Second, if blocking of `youtube_transcript_api` recurs (rather than being a one-off), add a rotating residential proxy (Webshare, per the maintainer's own tested recommendation) ahead of reaching for Gemini at all — this addresses the actual root cause (IP-level blocking) rather than routing around it with a different, less proven dependency. Third, if Gemini is added as a fourth-tier fallback, it must be implemented defensively, not naively: catch the `ClientError`/`ServerError`/`APIError` hierarchy explicitly, treat "no exception raised" as *not* synonymous with success by checking `response.prompt_feedback.block_reason` and inspecting `candidate.finish_reason`, cap retries specifically at HTTP 429 (with backoff) and at the documented first-call truncation bug (detected via a required "END OF TRANSCRIPT" marker in the prompt), and default to a fast/cheap model rather than a reasoning-tier one since the task is transcription-style, not analytical. A minimal code sketch synthesized from the sourced API shapes:

```python
from google import genai
from google.genai import types
from google.genai import errors as genai_errors

_TRANSCRIPT_PROMPT = (
    "Produce a transcript of the spoken audio in this video. "
    "Format EVERY line as `MM:SS — <text>`... "
    "Finish your output with a final line that says exactly: END OF TRANSCRIPT"
)


def fetch_transcript_gemini_fallback(video_url, *, api_key, model="gemini-2.5-flash", max_attempts=2):
    client = genai.Client(api_key=api_key)
    for attempt in range(1, max_attempts + 1):
        try:
            response = client.models.generate_content(
                model=model,
                contents=types.Content(
                    parts=[
                        types.Part(file_data=types.FileData(file_uri=video_url)),
                        types.Part(text=_TRANSCRIPT_PROMPT),
                    ]
                ),
                config=types.GenerateContentConfig(max_output_tokens=8192),
            )
        except genai_errors.ClientError as e:
            if getattr(e, "code", None) == 429 and attempt < max_attempts:
                continue  # backoff, then retry
            raise
        except genai_errors.ServerError:
            if attempt < max_attempts:
                continue
            raise
        if getattr(response, "prompt_feedback", None) and response.prompt_feedback.block_reason:
            raise RuntimeError(f"blocked: {response.prompt_feedback.block_reason}")
        text = getattr(response, "text", None)
        if text and "END OF TRANSCRIPT" in text:
            return text  # parse MM:SS lines downstream
    raise RuntimeError("Gemini fallback exhausted retries")
```

Even with this hardening, idea-catcher should log every Gemini fallback invocation's raw response shape to build its own failure catalog, since no comprehensive, authoritative list of failure modes exists in Google's own documentation — the picture above is assembled from scattered GitHub issues and forum threads, not a guaranteed-complete reference.

## Conclusion

The interesting shift here is not whether Gemini *can* substitute for scraped transcripts — it clearly can, technically — but that doing so trades a well-understood failure mode (YouTube blocking scraper-style access, with documented mitigations) for a less-understood one (Gemini's own server-side flakiness on video input, which nobody outside Google has fully characterized and which Google has not acknowledged fixing). A comparable production system independently reached the same conclusion and is moving away from Gemini for long-video work rather than toward it. Idea-catcher should treat Gemini video understanding as a capability worth having in reserve — cheap, free-tier-accessible, and architecturally sound — but rank it below proxy-hardening the existing scraper-based tiers, and wrap it in retry/truncation-detection logic strict enough to catch its most-reported failure mode: silently wrong output with no error at all.
