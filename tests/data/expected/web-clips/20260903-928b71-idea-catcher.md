## 📝 Summary

- Capture ideas on iPhone or Mac in Obsidian; use Web Clipper for browser content and AI chats.
- Sync incoming files to the `epiaku/epiaku-ideas` GitHub repository, with new notes and clips in `inbox/`.
- Run an hourly, non-real-time processor on Proxmox that moves each inbox file to `raw/` under a unique name before processing it.
- Use source metadata to select processing rules, write Hugo Markdown to `epiaku-docs`, and preserve original inputs in type-specific archives.
- Favor deterministic Python for Git, file handling, paths, and frontmatter; use local or cloud AI only where semantic processing is useful.
- Validate the workflow locally first, then consider a single-user cloud deployment and, later, a paid multi-user service.

## ✅ Decisions

- Keep Hugo with Docsy as the structured documentation site; use Obsidian primarily for capture and drafting.
- Use the Git community plugin by Vinzent03 (`vinzent03/obsidian-git`) for the Obsidian-to-GitHub workflow.
- Use `epiaku/epiaku-ideas` as the raw-input repository and keep new notes and Web Clipper captures in an `inbox/` folder, separate from root files such as `README.md`.
- Use three processing states: `inbox/` → uniquely named `raw/` → `archive/<type>/`; publish processed content to the separate `epiaku-docs` repository.
- Use Obsidian templates or clipper metadata, especially a `type` field, to distinguish short notes, AI chats, and web clips.
- Accept hourly processing rather than building a real-time webhook pipeline.
- For the local proof of concept, favor one scheduled Python job over an always-running n8n workflow, with the processing LXC started hourly and shut down after its job finishes.
- Develop the product in three phases: local personal workflow, cloud-hosted single-user workflow, then paid multi-user SaaS.

## 🔀 Options

- Capture by Obsidian and Git versus email, Slack, shortcuts, or GitHub Issues: Obsidian preserves an editable local note and raw Markdown; direct API capture can be quicker but needs connectivity or an explicit local-save fallback.
- GitHub files versus Issues as the intake queue: files fit the chosen staged raw archive; Issues offer built-in open/closed processing state but change the capture and archival workflow.
- Python job versus n8n or another orchestrator: Python fits scheduled, deterministic batch processing and self-termination; n8n offers a visual workflow and integrations but adds a persistent application and operational overhead.
- Separate LXCs versus a combined processing LXC: separate services provide isolation; one LXC is simpler for the small, single-user Proxmox workload.
- Always-on processor versus hourly LXC startup: always-on is immediately available; scheduled startup avoids idle runtime and is sufficient for a few notes per day.
- Deterministic Python versus local Needle versus a cloud LLM: Python handles predictable transformations, Needle is a candidate for local classification or extraction, and a larger LLM may be needed to synthesize long AI chats.
- For a future SaaS, user-owned GitHub repositories versus managed repositories: user-owned storage leaves capture methods and source ownership with the customer; managed storage reduces onboarding work but requires the service to provide ingestion and export.
- Private owner-only, invited-team, or public access to future SaaS-generated sites: the appropriate authorization and sharing model remains a product choice.

## ❓ Open Questions

- How should the processor map source topics to the actual existing Docsy sections, and when should it update an existing page rather than create a new one?
- What exact naming, collision checks, and retry rules will make the `inbox/` → `raw/` → published page → archive transitions safe after partial failures?
- How will Git synchronization remove processed inbox files from the phone without also downloading the growing `raw/` and `archive/` trees into the mobile vault?
- How will the iCloud-shared vault and Git synchronization across iPhone and Mac be arranged to avoid conflicting edits or duplicate sync activity?
- Has the mobile Git push been verified on GitHub? The chat confirms a clone/pull and a report of 23 committed files, but not a successful push of an inbox test note.
- Does the fine-grained token grant access to `epiaku/epiaku-ideas`? The user initially selected `epiaku-docs` when creating a token.
- How reliably can Web Clipper capture complete Gemini, ChatGPT, or Claude conversations, and what should happen when a clip contains only part of a chat?
- What backup and recovery procedure will cover the vault templates, `.obsidian` configuration, credentials, and both repositories?
- If the SaaS phase proceeds, what are the repository authorization, tenant isolation, site-access, billing, and AI-usage limits?

## 🧭 Purpose and current environment

The system is intended to catch startup app and SaaS ideas, YouTube ideas, reminders, web references, and AI conversations before they are forgotten. Epiaku Docs already uses Hugo with Docsy, stores its sources on GitHub, and is served locally from a Proxmox LXC. Access to the personal site is through the home UniFi VPN. The user prefers Docsy’s structured pages, navigation, search, and rich presentation for reading finished material; Obsidian is the capture workspace.

Obsidian is installed on iPhone and Mac. An iCloud-based Obsidian folder has been made accessible across those devices. The mobile Git plugin cloned `https://github.com/epiaku/epiaku-ideas.git`, and the user saw the repository’s README. Later, the plugin reported **23 files committed**. That report alone does not establish that those files were pushed successfully to GitHub.

## 🗺️ Intended local flow

```text
Obsidian on iPhone or Mac
  ├─ dictated or written notes
  ├─ browser clips and links
  └─ captured AI chats
          │ Obsidian Git sync
          ▼
GitHub: epiaku/epiaku-ideas
  inbox/ ──► raw/ ──► archive/<type>/
              │          ▲
              │ Python processing and publication
              ▼
GitHub: epiaku-docs/content/<appropriate section>/
              │ periodic local pull and Hugo rebuild
              ▼
Local Docsy site on Proxmox, accessed over VPN
```

The proposed Proxmox host schedule starts a processing LXC about once per hour. A Python job in that LXC pulls current inputs, works through pending files, and shuts the LXC down once the job finishes. This replaced the earlier proposal for an always-on n8n service; the processing LXC and job have not yet been reported as implemented. The local Hugo deployment also needs its own periodic pull and rebuild after `epiaku-docs` changes.

## 📥 Capture and source metadata

The Git repository and Obsidian vault have corresponding paths: the Git plugin does not map the entire vault root to a remote `inbox/` subfolder. Because the repository root contains files such as `README.md`, create `inbox/` in the vault and set Obsidian’s default new-note location to that folder. Set the Web Clipper template’s note location to `inbox/` as well; it previously saved clips under `Clippings/`.

Templates provide a lightweight processing hint. Proposed source types include `voice-note`, `ai-chat`, and `web-clip`, with a potential separate YouTube type. A note can also supply a topic hint such as “YouTube:” or “App Idea:” to help place it within the existing site. The source type determines the processing approach; the topic determines the destination page or section. The actual site paths and classification rules still need to be based on the real `epiaku-docs` layout.

| Input | Intended treatment |
| --- | --- |
| Short dictated or written note | Preserve the idea while cleaning obvious speech artifacts; use a standard page format. |
| AI conversation | Condense a potentially long exchange into decisions, compared approaches, useful technical detail, and unresolved questions. |
| Web article or YouTube reference | Preserve its source URL and the user’s reason for saving it; create an appropriately attributed reference or idea. |

The Web Clipper is working with the `Epiaku` vault and currently saves chat captures in `Clippings/`. Its default filename, `New chat`, is not descriptive. The proposed clipper template would choose an inbox location, add source metadata, and use a timestamped name; the processor would still assign the authoritative unique filename at the `raw/` stage. Complete capture of long browser chats was suggested in the conversation but not verified.

## 🔄 Processing and recovery boundaries

The first processing stage moves each synced inbox file to `raw/` under a collision-resistant name containing a timestamp, unique identifier, and short descriptor or type. This is deliberately separate from AI processing: once an input is staged, its original text remains available for inspection, testing, and replay. The next stage reads `raw/`, chooses rules using its metadata, produces or updates Hugo Markdown, commits the result to `epiaku-docs`, and moves the source to `archive/<type>/` only after successful publication.

Python is responsible for predictable operations: parsing metadata, assigning names and paths, assembling valid Hugo frontmatter, manipulating files, and making Git commits. Needle was discussed as an **optional** local model for structured classification or metadata extraction on the Odroid H4 Proxmox host. A cloud LLM was discussed for work such as synthesizing long AI chats; the chat does not establish that Needle can perform that task or that every input needs an AI call.

Staging and archiving support retries, but **idempotency is not automatic**. The implementation still needs a stable relationship between a raw input and its published output, checks before creating or updating a page, and an order of Git writes that remains recoverable if one repository push succeeds and the other fails. Pending files in `raw/` must be checked on later runs even when `inbox/` is empty.

## 📱 Synchronization behavior to verify

The mobile plugin’s **Auto commit-and-sync interval** was set to 10 minutes. In the conversation, this setting was described as combining commit, pull, and push while the iPhone app is active; its separate auto-push interval was greyed out. iOS may suspend the app, so an interval should not be treated as guaranteed background delivery after the phone is locked. Auto-pull on startup concerns a fresh app launch, not necessarily every switch back to an app still running in memory.

A Git pull propagates repository moves back into the phone’s vault. Moving a file from `inbox/` to `raw/` therefore clears the **inbox**, but may leave the file present on the phone under `raw/`; later archiving may similarly bring `archive/` onto the phone. This does not yet meet the stated preference for a one-way capture buffer whose processed files disappear from the device. The earlier suggestion to add tracked archive files to `.gitignore` does not, by itself, prevent Git from pulling them. Mobile storage and synchronization boundaries need a deliberate design before relying on automatic cleanup.

The fine-grained GitHub token was initially scoped to `epiaku-docs`, while the cloned capture repository is `epiaku/epiaku-ideas`. Its repository scope and **Contents: read and write** permission need to be checked against the repository actually being pushed to. Credentials should not be committed with vault settings or templates.

## 🖥️ Processing deployment and later phases

For the local proof of concept, a single scheduled Python-processing LXC is the latest recommendation. It avoids running separate always-on n8n, Needle, and Python service containers for an hourly, low-volume workload. An n8n workflow remains an alternative if visual orchestration or additional integrations become more valuable than a short-lived code job. Any self-terminating job must finish or safely record its work before shutting down; a fixed cron shutdown time was rejected because processing duration can vary.

The product progression discussed was:

| Phase | Scope | Main work |
| --- | --- | --- |
| 1. Local personal workflow | Obsidian, GitHub, Proxmox processing, local Hugo/Docsy site | Validate capture, routing, output quality, retries, and deployment. |
| 2. Cloud, still single-user | Move processing and site delivery to cloud infrastructure | Test reliability and cloud operations before adding customers. |
| 3. Paid multi-user SaaS | Customer repositories or managed storage; protected generated sites | Add onboarding, repository authorization, tenant isolation, sharing controls, and billing. |

For a bring-your-own-repository service, customers could choose Obsidian or any other way to place inputs in GitHub. A managed-storage offering would also need to provide capture methods. The conversation favored investigating a scoped GitHub App over collecting customers’ personal access tokens. Sites might be owner-only, shared with an invited team, or public; none of those SaaS designs has been selected or built.
