# YouTube transcript fetching: research on `last30days-skill`

**Analysed:** 2026-09-29
**Source:** [github.com/mvanhorn/last30days-skill](https://github.com/mvanhorn/last30days-skill) (cloned shallow, read-only; no code from it was copied into this repo)
**Why:** our own transcript fetch (`src/catcher/modules/youtube/facts.py`) gets blocked by YouTube (429 on both `youtube_transcript_api` and the yt-dlp caption fallback) from this dev machine's IP. `last30days-skill` claims to read YouTube transcripts for keyword extraction, so it was worth seeing how it does that and whether any of it applies to us.

## What we were blocked by

From a real run (2026-09-29): `yt-dlp`'s own video-info call succeeds (title, views, likes, subscribers all come back fine), but **both** caption-fetch paths 429:

- `youtube_transcript_api`'s own request.
- our yt-dlp-based fallback (`_fetch_transcript_via_ytdlp`, which asks yt-dlp for `requested_subtitles` and fetches the caption URL through yt-dlp's own HTTP client).

So the block is specifically on YouTube's caption-serving endpoint, from this IP, not a general YouTube block (browsing and yt-dlp's own metadata calls are unaffected).

## How `last30days-skill` gets transcripts

Its `skills/last30days/scripts/lib/youtube_yt.py` cascades through several independent methods per video, falling through in order:

1. **yt-dlp with `--extractor-args youtube:player_client=android`** (the default, unless `LAST30DAYS_YT_PLAYER_CLIENT` is set to something else or emptied). This tells yt-dlp to impersonate YouTube's Android app client instead of the web client. The Android client talks to a different, less bot-gated backend and gets past YouTube's throttle **without cookies**. Their own docs: "Default is `android`, which bypasses the web bot-gate without cookies." This is the single biggest thing our `facts.py` doesn't do — we call yt-dlp with only `skip_download`/`quiet`/`no_warnings`/`writeautomaticsub` params, no `player_client` override.
2. **A direct-HTTP fallback with no yt-dlp at all** (`_fetch_transcript_direct`): fetch the plain watch page (`https://www.youtube.com/watch?v=<id>`) with a realistic browser `User-Agent` and `Accept-Language` header, regex out the `ytInitialPlayerResponse` JSON blob embedded in the page's `<script>` tags, walk it to `captions.playerCaptionsTracklistRenderer.captionTracks`, pick the English track's `baseUrl`, and fetch that with `&fmt=vtt` appended. This is the same data our `_fetch_transcript_via_ytdlp` gets from yt-dlp's `requested_subtitles`, just reached by scraping the watch page directly instead of asking yt-dlp to resolve it — a genuinely independent path (no yt-dlp extractor involved) for when yt-dlp itself is blocked.
3. **SSH routing to a different machine** (`LAST30DAYS_YOUTUBE_SSH_HOST`): when running from a blocked datacenter/cloud IP, it SSHes to a named host (their docs mention "residential IP egress" and a Mac mini) and runs yt-dlp there instead, piping the VTT back over SSH (`ssh -o BatchMode=yes -- <host> '<remote yt-dlp script>'`). This is exactly our own documented plan (fetch from Proxmox at home, never from a blocked cloud/CI IP — see [idea-catcher-pipeline.md](idea-catcher-pipeline.md)), just implemented as a generic env-var-driven remote-exec rather than hardwiring the worker's location.
4. **A paid fallback (ScrapeCreators API)**, spent only on a genuine hard failure (429/bot-gate), never on a video confirmed to have no captions at all (`_should_try_sc_transcript` checks a `no_caption_tracks` flag first, to avoid wasting a credit on a video that genuinely has none). Third-party scraping-as-a-service; adds cost and an external dependency.
5. **Whisper transcription** (`skills/last30days/scripts/lib/transcribe.py`) as a structurally different fallback for genuinely caption-less videos: download audio via yt-dlp (apparently more reliable than the caption endpoint), re-encode to a low-bitrate mono stream, chunk if still over Whisper's 25 MB upload limit, transcribe each chunk through Groq's free Whisper tier first, then OpenAI's paid Whisper as backstop, and join the pieces. Their own docs mark this "groundwork: module shipped, not yet auto-invoked by the engine."

### Supporting resilience details

- **Transient vs. genuine-no-captions classification.** Two regexes on yt-dlp's stderr: `_TRANSIENT_RE` (`429|too many requests|sign in to confirm|not a bot|rate.?limit|...|timeout|connection|...`) means "worth retrying, definitely not a real no-captions case"; `_NO_CAPTION_RE` (`no subtitles|requested (format|language)|...`) means "stop, don't retry, don't fall through to a paid fallback." Their comment: "a non-zero yt-dlp exit means a real fetch error (rate-limit / bot-check / network), NOT 'no captions' — yt-dlp exits 0 with no file for a video that genuinely lacks the requested captions."
- **Partial-result salvage.** yt-dlp downloads requested caption languages sequentially (they default to `en,es,pt`). A later language 429ing after an earlier one succeeded still leaves a usable VTT on disk. Both on a timeout and on a non-zero exit, they check disk for _any_ matching VTT before treating the attempt as a failure — "this is the root cause of the 0/N transcript runs reported when every video had captions," per their own comment.
- **Jittered per-video backoff.** Retry delay is `base * (attempt + 1) + offset`, where `offset` is a `0.0–1.0s` value derived from a hash of the video id, so parallel workers retrying the same failure don't all retry in lockstep and re-trip the rate limiter together.
- **Process-wide concurrency cap.** A semaphore limits concurrent yt-dlp processes to 2, so a fan-out over many videos in one run doesn't stampede the same throttled IP.

## What applies to us, and what doesn't

| Idea                                                      | Applies to idea-catcher?                             | Why                                                                                                                                                                                                                                                                                                                                          |
| --------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `player_client=android`                                   | **Tested 2026-09-29 — confounded, worth retesting.** See below. | Failed on a stale (9-months-old) yt-dlp build with PO-token/`nsig` errors unrelated to the actual problem. After updating yt-dlp, those errors disappeared and the real issue turned out to be a plain `429` on the caption-download request itself — untested against `android`/other clients on the current yt-dlp build yet. See "What to test next." |
| Direct-HTTP watch-page scrape (`ytInitialPlayerResponse`) | Worth having as a third fallback path.               | Genuinely independent of yt-dlp's extractor, unlike our current two paths which both go through yt-dlp. More fragile long-term: YouTube can reshape that embedded JSON without notice, and yt-dlp's maintainers track that churn for us — a bare scrape doesn't get that maintenance for free.                                               |
| SSH-routing to a home/Proxmox machine                     | Already our own plan, nothing new conceptually.      | Matches "fetch at home, never from a blocked cloud IP" already documented in [idea-catcher-pipeline.md](idea-catcher-pipeline.md). Their implementation (env-var-driven `ssh <host> <yt-dlp script>`) is a reasonable shape to copy if we ever run the pipeline from more than one place.                                                    |
| Paid ScrapeCreators fallback                              | **No, skip it.**                                     | We already chose to defer `youtube` documents rather than pay for a low-quality (no-transcript) summary. Adding a paid third-party scraping API as a dependency just to avoid that defer cuts against that decision.                                                                                                                         |
| Whisper transcription fallback                            | Keep in mind as a last resort, not a near-term pick. | Structurally different: sidesteps YouTube's caption endpoint entirely by transcribing downloaded audio ourselves. Bigger lift (audio download + compression/chunking + a paid/free Whisper call per video) than the API-level tricks above. Worth it only if `player_client=android` and the scrape fallback both stop holding up over time. |
| Transient-vs-no-captions stderr classification            | We already do a version of this.                     | Our `_best_effort_transcript` in `facts.py` already distinguishes "both sources failed" (now deferred, per our recent decision) from "genuinely no captions" via exceptions rather than regexes on stderr text; not a gap.                                                                                                                   |
| Partial-VTT salvage, jittered backoff, concurrency cap    | Low priority for us right now.                       | These matter at their scale (tens of videos per run, comparison-mode fan-out). We process one YouTube document at a time; not worth the complexity until/unless we start batching many videos per run.                                                                                                                                       |

## Recommended next steps, cheapest first

1. ~~Try `player_client=android` in `facts.py`~~ — **tested 2026-09-29, initially failed**, but that turned out to be a confound from a stale local yt-dlp build, not a real dead end. See [the command-line test log](idea-catcher-youtube-transcript-cli-tests.md) for the full trail.
2. **Keep yt-dlp current wherever the pipeline actually runs** (worker machine, not just a dev MacBook) — a stale build was independently masking the real 429 behind unrelated PO-token/`nsig` errors during testing.
3. **Isolate whether the 429 is time-windowed or a hard IP-level throttle** before writing any code — cool-down + retry, a fresh never-requested video id, and a re-sweep of `player_client` values on a current yt-dlp build. See "What to test next" in [the command-line test log](idea-catcher-youtube-transcript-cli-tests.md) for the exact commands and where this stands.
4. **If the 429 turns out to be a genuine, persistent throttle**, add the direct-HTTP watch-page scrape (`ytInitialPlayerResponse` → caption track `baseUrl` → `&fmt=vtt`) as a third fallback path in `_best_effort_transcript`, alongside the existing `youtube_transcript_api` and yt-dlp-caption paths. Needs a realistic `User-Agent` header, nothing else new.
5. **Only if that keeps failing too**, revisit SSH-routing the fetch to a home/Proxmox machine (already the documented plan), or a Whisper-based audio-transcription fallback (video/audio *download* formats resolve fine even when the caption endpoint 429s, per the command-line tests, so this path isn't blocked by the same wall). Both are bigger changes; not warranted until the cheaper options are proven insufficient.
